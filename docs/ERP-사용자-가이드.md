# 디지털스퀘어 ERP 사용자·테스트 가이드

문서 버전: Phase 6 운영 산출물 / 2026-09-28  
대상: 처음 시스템을 접하는 직원, 팀장·PM, 영업·재무·인사 관리자, 테스트 담당자

## 1. 시스템을 한 문장으로 이해하기

이 ERP는 **직원이 회사에 합류한 순간부터 근태·휴가·업무·프로젝트를 수행하고, 고객 접점이 견적과 계약을 거쳐 프로젝트·청구·세금계산서·수금·손익·마감으로 끝날 때까지의 기록을 하나의 흐름으로 연결**합니다.

앞 단계의 확정 데이터를 다음 단계가 재사용합니다. 승인 견적은 계약의 근거가 되고, 계약은 프로젝트와 청구 일정의 근거가 되며, 프로젝트의 실제 업무시간과 승인 비용은 손익과 마감의 근거가 됩니다.

## 2. 회사 전체 프로세스 지도

```text
[조직·직원·권한]
 ├─ [근무정책] → [출퇴근] → [근태 현황·정정]
 ├─ [휴가 잔액] → [휴가 신청] → [결재] → [근태 반영]
 ├─ [자산 지급] → [회사 PC 등록] → [출퇴근 기기·네트워크 검증]
 └─ [인력 프로필] → [리소스 계획] → [프로젝트 투입]

[고객사] → [영업기회] → [견적 Revision·승인] → [계약·서명]
                                               ↓
 [업무일지·주간보고] ← [프로젝트 허브] → [문서·검수·완료]
                              ├─ [청구 일정] → [청구서] → [세금계산서 발행자료]
                              │                         → [홈택스/ASP 실제 발급·승인번호]
                              ├─ [입금 등록] → [청구별 수금 배분] → [미수금]
                              ├─ [법인카드·기타 비용] → [승인·지급]
                              └─ [공수+비용+매출] → [프로젝트 손익] → [마감]

[알림·메일]은 단계 전환을 전달하고, [감사 로그]는 누가 무엇을 바꿨는지 남깁니다.
```

## 3. 처음 로그인한 사람이 알아야 할 원칙

1. 보이는 메뉴는 계정의 역할과 권한에 따라 다릅니다.
2. 같은 역할명이라도 조직 범위가 다르면 조회 데이터가 달라집니다.
3. 다른 사용자가 먼저 저장하면 `409 Conflict`가 날 수 있습니다. 새로고침 후 다시 확인합니다.
4. 삭제 대신 취소·보관·반려·재개방처럼 이력을 보존하는 상태 전이를 사용합니다.
5. 검색·Excel·PDF도 현재 계정의 DB 권한(RLS)을 따릅니다.
6. 개인정보, 비밀번호, 서비스 키, 카드 전체 번호는 이슈 문서나 화면 캡처에 넣지 않습니다.

## 4. 역할별 시작점

| 사용자 | 먼저 볼 화면 | 주 업무 |
|---|---|---|
| 일반 직원 | 대시보드, 내 근태, 업무일지 | 출퇴근, 휴가, 비용, 일일 업무와 주간보고 |
| 팀장 | 대시보드, 결재함, 주간보고 | 팀 휴가 결재, 업무 현황, 인력 상태 확인 |
| 프로젝트 관리자 | 프로젝트, 리소스 계획, 손익 | 투입 인력, 문서·검수, 공수·비용·손익·마감 |
| 영업 담당 | 고객사, 영업기회, 견적 | 고객 기준정보, 영업 단계, 견적 Revision |
| 승인자 | 결재함, 견적, 계약 | 견적·계약 승인과 상태 확인 |
| 재무 담당 | 청구 일정, 청구·미수금, 세금계산서, 입금 | 청구계획, 발행자료, 수금배분 |
| 인사/관리자 | 가입 승인, 직원·조직·근태·휴가 | 계정 활성화, 역할·조직, 잔액·근태 관리 |
| 시스템 관리자 | 역할관리, 설정, 감사 로그, 통합 보고서 | 최소권한, 자동화·감사 점검 |

## 5. 공통 화면 사용법

- 왼쪽 메뉴는 업무 영역별로 묶여 있고 현재 위치는 강조 표시와 상단 경로로 확인합니다.
- 상단 통합 검색은 고객명, 업무 코드, 프로젝트명, 문서번호를 두 글자 이상 입력합니다.
- `+` 빠른 작업은 현재 권한으로 가능한 등록 작업만 보여 줍니다.
- 종 모양은 읽지 않은 알림 수입니다. 알림을 열면 관련 업무로 이동합니다.
- Excel/PDF 다운로드는 데이터를 변경하지 않으며 출력 시점과 기준일을 기록합니다.

## 6. 조직·계정·권한

### 회원가입과 활성화

1. 사용자가 회원가입하고 이메일을 확인합니다.
2. 계정은 `REQUESTED(승인 대기)`로 생성됩니다.
3. 관리자가 `가입 승인`에서 사번, 입사일, 소속을 지정하고 승인합니다.
4. 직원 상세에서 직급, 직책, 시스템 역할을 각각 지정합니다.
5. 사용자가 다시 로그인해 메뉴를 확인합니다.

직급·직책은 인사 표시이고 시스템 역할은 권한 묶음입니다. 역할은 여러 개 지정할 수 있습니다. 관리자는 직원 상세에서 임시 비밀번호 초기화를 수행할 수 있으며, 초기값은 별도 안전한 채널로 전달하고 사용자가 즉시 변경하도록 안내합니다.

### 조직과 역할

- 조직은 트리 구조이며 순환 이동은 차단됩니다.
- 조직 리더는 결재 경로와 팀 범위 조회에 사용됩니다.
- 활성 직원이나 하위 조직이 남은 조직은 바로 비활성화할 수 없습니다.
- 마지막 활성 ADMIN 역할은 제거할 수 없습니다.

### 테스트

- 승인 대기 사용자는 대시보드에 진입하지 못해야 합니다.
- 직원 계정에서 관리자 URL을 직접 열면 403이 나와야 합니다.
- 역할 변경 후 재로그인했을 때 메뉴와 API 권한이 함께 바뀌어야 합니다.

## 7. 근무정책·출퇴근·근태

근무정책은 근무 시작·종료, 휴게시간, 허용 요일, 출퇴근 검증 방식을 특정 기간에 적용하는 기준입니다. 과거 판정을 바꾸지 않도록 새 버전과 적용 시작일로 관리합니다.

### 출퇴근 절차

1. 관리자가 직원에게 정책 기간을 배정합니다.
2. 회사 PC를 자산과 직원에게 지급하고 장치를 등록합니다.
3. `출퇴근 검증`에서 회사 공인 CIDR과 정책을 설정합니다.
4. 직원이 `내 근태`에서 출근을 누르면 서버시각, 등록 장치, 회사 네트워크를 검증합니다.
5. 같은 근무일에 퇴근을 한 번 기록합니다.
6. 관리자는 지각·결근·휴가·보정 이력을 확인합니다.

실패 시 정책 배정 → 자산 지급/장치 revoke → Agent heartbeat/증거 만료 → 회사 CIDR과 실제 ingress IP 순서로 확인합니다. `localhost` 개발용 IP는 운영 신뢰 설정을 대신하지 않습니다.

## 8. 휴가·결재·알림

휴가 잔액은 단순 숫자를 덮어쓰지 않고 부여·조정·예약·반환·사용 원장의 합계로 계산합니다. 관리자는 `GRANT(부여)` 또는 `ADJUST(조정)`를 등록하며 차감은 음수 조정으로 기록합니다.

1. 직원이 휴가 초안을 작성합니다.
2. 제출하면 연차가 예약되고 조직 리더 기준 결재 경로가 스냅샷으로 저장됩니다.
3. 결재자가 순서대로 승인/반려합니다.
4. 최종 승인 시 사용이 확정되고 근태에 `VACATION` 또는 `HALF_DAY`로 반영됩니다.
5. 반려·제출 취소 시 예약 잔액이 반환됩니다.

잔액보다 큰 신청, 겹치는 휴가, 현재 결재자가 아닌 사용자의 승인은 차단되어야 합니다. 메일 provider가 꺼져 있어도 인앱 알림과 outbox는 보존됩니다.

## 9. 자산·장치

자산은 노트북·모니터 등의 현재 상태와 지급·반납 이력을 관리하고, 장치는 출퇴근 신뢰용 회사 PC credential과 heartbeat를 관리합니다.

1. 자산 등록 → 직원 지급 → 필요 시 장치 등록·토큰 1회 전달
2. Agent heartbeat 확인 → 출퇴근 검증
3. 반납 시 열린 지급 이력 종료 → 장치 revoke

동일 자산을 두 명에게 동시에 지급할 수 없고 토큰 원문은 다시 조회할 수 없습니다.

## 10. 인력 프로필·리소스 계획

- `내 인력프로필`: 학력, 기술, 자격, 수행경력
- `인력 기술 현황`: HR/Admin 또는 실제 관리 범위에서 후보 조회
- `리소스 계획`: 기간이 겹치는 투입률을 합산해 과투입 확인
- `프로젝트 > 리소스`: 요구 역할·기술·인원과 실제 배정 연결

WARN 정책은 경고 후 저장할 수 있고 BLOCK 정책은 한도를 넘는 저장을 막습니다. 개인정보 포함 Excel은 접근 제한 위치에 보관합니다.

## 11. 업무일지·주간보고

업무일지는 하루에 실제 수행한 업무와 시간의 원장이며 출퇴근 기록과는 별도입니다. 프로젝트 공수 원가의 근거가 됩니다.

1. 날짜, 업무 구분, 프로젝트, 제목, 수행시간, 진행상태를 입력합니다.
2. 전날 복사 후 실제 내용과 시간을 수정할 수 있습니다.
3. 월~금 업무를 바탕으로 주간보고를 생성/새로고침합니다.
4. 이슈, 주간 요약, 차주 계획을 작성하고 확정합니다.
5. 확정 시 스냅샷이 남아 이후 업무일지 수정이 과거 보고를 바꾸지 않습니다.
6. 팀장은 조직 필터와 보고 모드로 회의하고 Excel로 보관합니다.

## 12. 고객·영업·견적·계약

### 고객사

고객사는 이후 모든 영업·청구 문서의 기준정보입니다. 상호, 사업자등록번호, 대표자, 주소, 업태·종목, 계산서 수신 이메일을 정확히 관리합니다. 필수 세무정보가 비면 세금계산서 초안 생성을 차단합니다.

### 영업기회

영업기회는 아직 계약되지 않은 매출 가능성입니다. 일반 흐름은 `LEAD → QUALIFIED → PROPOSAL → NEGOTIATION → WON/LOST`이며 예상금액 × 확률을 기대매출로 봅니다.

### 견적 Revision과 승인

1. 영업기회에서 견적을 생성합니다.
2. Header에 견적일, 유효기간, VAT, 예상원가를 입력합니다.
3. Detail에 역할/항목, 인원, MM, 기간, 수량, 단가를 입력합니다.
4. 내부 승인 요청 시 현재 Revision이 잠기고 결재함으로 전달됩니다.
5. 수정이 필요하면 기존 Revision을 보존한 새 버전을 만듭니다.
6. `견적서 PDF`로 승인 상태와 Revision이 표시된 문서를 출력합니다.

승인 전 PDF에는 승인 전 표기가 있으므로 외부 확정본으로 사용하지 않습니다.

### 계약·발주

승인 견적을 계약 초안으로 전환하고 계약기간·금액·청구 조건을 확인합니다. 내부 승인 후 실제 서명 정보를 기록하고 서명된 계약에서 프로젝트를 생성합니다. 원 견적 Revision과 승인 이력은 계속 보존됩니다.

## 13. 프로젝트 허브

프로젝트는 계약 이행의 중심으로 투입 인력, 업무일지, 문서, 검수, 비용, 청구, 손익과 마감을 같은 ID로 연결합니다.

- `개요`: 기간, 고객, 상태, PM, 연결 현황
- `리소스`: 역할별 MM, 원가·청구 단가 snapshot, 실제 배정
- `문서`: 계약서, 착수, 산출물, 검수, 보고서의 버전·해시·분류
- `검수`: 요청, 피드백, 재검수, 승인/반려와 증빙
- `보고`: 확정 주간보고 중 이 프로젝트 업무
- `손익`: 계약·청구·수금·공수·비용의 기준일 집계
- `마감`: 미완료 검수·미청구·미수·비용·필수문서를 한 번에 점검

문서는 공개 URL이 아니라 세션과 권한을 거쳐 다운로드합니다. 마감 후 원장 변경은 제한되며 재개방에는 사유와 권한이 필요합니다.

## 14. 비용·법인카드

통합 비용 원장은 법인카드, 현금, 계좌이체, 세금계산서성 비용을 프로젝트별로 기록합니다. 거래일, 비용 유형, 거래처, 공급가액, VAT, 총액, 목적, 영수증을 입력하고 제출→승인/반려→지급으로 전환합니다. 손익에는 승인된 비용만 반영됩니다.

법인카드 월 정산은 카드와 프로젝트 기간 배정 → 사용내역/영수증 → 월 데이터 생성 → 검토·마감 → 행정 양식 Excel/체크섬 → 메일 첨부 발송 순서입니다. 수정이 필요하면 재개방 사유를 남깁니다.

## 15. 청구·세금계산서·수금

### 청구 일정이란 무엇인가

청구 일정은 **계약 체결과 실제 청구서 발행 사이의 계획 단계**입니다. “언제, 어떤 조건이 충족되면, 얼마를 청구할 것인가”를 착수금·중도금·잔금 또는 월별 대금으로 구조화합니다.

예: 계약 공급가액 1억원을 `계약 후 30%`, `중간검수 후 40%`, `최종검수 후 30%`로 나눕니다. 일정은 예상 현금흐름과 준비목록이며 아직 실제 청구 발행은 아닙니다.

### 실제 업무 흐름

1. `청구 일정`: 계약·프로젝트, 차수, 조건, 예정일, 공급가액, VAT를 등록합니다.
2. 조건 충족 후 일정에서 청구서 초안을 생성합니다.
3. `청구 · 미수금`: 청구일, 입금기한, 수금계좌를 확인하고 발행합니다.
4. `세금계산서`: 발행자료를 생성하고 품목·작성일·공급일·수신 이메일을 검토해 READY로 확정합니다.
5. 홈택스, ASP 또는 인증 ERP에서 실제 전자세금계산서를 발급합니다.
6. 국세청 24자리 승인번호와 발급 채널을 ERP에 기록해 ISSUED로 완료합니다.
7. `입금 · 수금배분`: 통장 입금을 등록하고 청구서에 전액/부분 배분합니다.
8. 배분 합계에 따라 미수잔액이 계산되고 기한을 넘기면 OVERDUE로 표시됩니다.

발급 전 PDF는 **홈택스 입력과 사내 검토용 발행자료**이며 법적 전자발급 완료 증빙이 아닙니다. 발급 완료 여부는 홈택스/등록 ASP 기록과 승인번호로 최종 확인합니다.

입금과 배분을 분리하는 이유는 한 입금이 여러 청구를 합쳐 지급하거나 한 청구를 여러 차례 나눠 지급할 수 있기 때문입니다.

## 16. 프로젝트 손익·마감

손익은 선택한 기준일까지 계약 공급가액, 청구·세금계산서·수금·미수, 업무일지 공수 원가, 승인 비용, 총원가, 매출총이익과 예측 손익을 같은 프로젝트로 모읍니다.

프로젝트 마감은 삭제가 아니라 **그 시점의 체크리스트와 재무 snapshot을 고정하는 통제 단계**입니다. 미완료 검수, 남은 청구 일정, 미발급 세금계산서, 미수금, 미승인 비용, 필수 문서가 있으면 항목별로 실패 원인을 보여 줍니다.

## 17. 통합 보고서·자동화

`통합 보고서` Excel은 권한에 따라 영업 파이프라인, 견적, 청구 일정, 청구·미수, 수금배분, 프로젝트 손익 시트를 만듭니다.

운영 자동화는 평일 오전 실행을 권장합니다. 7일 내 청구 예정과 기한이 지난 미수금을 찾아 담당자 인앱 알림 및 메일 outbox에 넣습니다. 같은 일정/청구/수신자 조합은 중복 생성하지 않고 실행 이력은 보고서 화면에서 확인합니다.

## 18. 감사·보안

감사 로그는 누가 언제 무엇을 바꿨는지 확인하는 운영 기록입니다. 원문 비밀번호, 서비스 키, 카드 전체 번호를 저장하거나 로그에 출력하지 않습니다.

- 운영 `.env`와 실데이터 Excel은 Git에 커밋하지 않습니다.
- 외부 PC 접속 시 `APP_URL`, `APP_ALLOWED_ORIGINS`, Supabase redirect allowlist의 스킴·호스트·포트를 맞춥니다.
- 운영은 HTTPS를 사용하고 공유 PC 사용 후 로그아웃합니다.

## 19. 로컬 테스트 환경 준비

### 최초 1회

```powershell
Set-Location C:\Users\<사용자>\projects\dtappsquare-erp
npm ci
npx supabase start
Copy-Item .env.example .env.local
npx supabase status
```

`.env.local`에 로컬 Supabase URL/키, 12자 이상 `SEED_PASSWORD`, `APP_URL=http://localhost:3000`을 입력합니다.

```powershell
npm run seed:local
npm run dev
```

- 앱 `http://localhost:3000`
- DB 관리 `http://127.0.0.1:55323`
- 로컬 메일 `http://127.0.0.1:55324`
- 계정 `admin@digitalsquare.local`, `manager@digitalsquare.local`, `employee@digitalsquare.local`
- 비밀번호는 로컬 `SEED_PASSWORD`

다시 시작할 때는 Docker Desktop → `npx supabase start` → `npm run dev` 순서입니다. 데이터를 유지하려면 `db reset`을 사용하지 않고 새 migration만 `npx supabase migration up --local`로 적용합니다.

## 20. 처음 보는 테스트 담당자의 권장 시나리오

### A. 계정과 권한

신규 가입·메일 확인 → ADMIN 승인·역할 부여 → 직원/관리자 메뉴 차이 → 권한 없는 URL/API 403을 확인합니다.

정책·장치·네트워크 준비 → 출퇴근 → 업무일지 2건 → 휴가 신청/팀장 승인 → 주간보고 생성·확정·Excel을 확인합니다.

### C. 영업에서 프로젝트 생성

고객사 → 영업기회 → 견적 Header/Detail → 승인 요청/승인 → 승인 PDF → 계약 승인·서명 → 프로젝트 생성 순서로 확인합니다.

### D. 프로젝트 수행

PM/직원 배정과 과투입 경고 → 계약서·산출물 문서 → 검수 요청·완료 → 프로젝트 업무일지 → 비용 등록·승인 순서입니다.

### E. 청구에서 수금·마감

7일 내 일정과 기한 경과 청구 준비 → Runbook endpoint 호출 → 실행 이력·알림함·Mailpit 확인 → 같은 날짜 재실행 중복 방지 → 잘못된 secret 401을 확인합니다.

## 23. 자주 발생하는 오류

| 현상 | 먼저 확인할 것 |
|---|---|
| localhost는 로그인되고 LAN IP는 안 됨 | `APP_ALLOWED_ORIGINS`, Supabase redirect URL, 서버 재시작, Origin |
| 로그인 401 | 이메일 확인, 직원 ACTIVE, 비밀번호, Auth와 employee 연결 |
| POST 400 | 필수값·날짜·금액·현재 상태, 화면 request ID |
| POST 403 | 역할/권한, 조직·프로젝트 범위, `APP_URL`/Origin |
| 409 Conflict | 다른 사용자/탭의 변경, 새로고침 후 version 재확인 |
| 출퇴근 차단 | 정책, 장치 heartbeat, 자산 지급, CIDR, 실제 ingress IP |
| 세금계산서 생성 실패 | 공급자 설정, 고객 사업자 정보와 이메일, 청구 상태 |
| Excel/PDF가 비어 있음 | 기준일, 필터, 현재 계정 조회 권한 |
| 메일이 안 옴 | 인앱 알림, outbox, provider, dispatcher, Mailpit |

## 24. 용어집

- **RLS**: 사용자와 업무 범위에 따라 DB 행 조회를 제한하는 정책
- **Revision**: 이전 견적을 보존한 새 버전
- **MM**: 1명이 한 달 투입되는 양을 1로 보는 Man-Month
- **청구 일정**: 계약 이후 실제 청구 전 조건·예정일·금액 계획
- **청구서**: 고객 대금 요청과 미수금 관리의 기준 원장
- **수금배분**: 실제 입금액을 하나 이상의 청구에 연결하는 작업
- **Outbox**: 업무 transaction과 메일 전송을 분리한 재시도 가능 원장
- **Snapshot**: 확정 시점 데이터를 이후 원본 변경과 분리해 고정한 기록
- **Request ID**: 서버 오류 한 건을 로그와 연결하는 식별자
