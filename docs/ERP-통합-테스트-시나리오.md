# 디지털스퀘어 ERP 전체 통합 테스트 시나리오

문서 버전 2026년 9월 28일

대상 관리자 인사 담당자 영업 담당자 팀장 프로젝트 관리자 재무 담당자 테스트 담당자

## 테스트 목적

이 문서는 빈 회사 환경에서 직원과 조직을 준비하고 실제 프로젝트 한 건을 수주 수행 청구 수금 마감하는 전 과정을 검증한다. 테스트 담당자는 이 문서의 순서를 바꾸지 않고 진행한다. 한 단계가 실패하면 단계 ID와 화면 주소 실제 결과 오류 메시지 Request ID를 Excel에 기록한다. 다음 단계가 실패한 단계의 데이터에 의존하면 수정 후 재검증할 때까지 진행을 멈춘다.

## 회사 업무 흐름

```text
회사 운영 기반 준비
조직과 역할 설정 → 직원 가입과 승인 → 근무정책과 자산 준비

직원 업무 준비
출퇴근 → 휴가와 결재 → 인력 프로필 → 업무일지와 주간보고

매출 기회 확정
고객사 → 영업기회 → 견적과 승인 → 계약과 서명

계약 이행
프로젝트 생성 → 인력 배정 → 문서와 산출물 → 검수 → 비용 집계

매출 실현
청구 일정 → 청구 발행 → 세금계산서 발행 → 입금과 수금배분

프로젝트 종료
손익 확인 → 미완료 항목 해소 → 프로젝트 마감 → 통합 보고서와 감사 확인
```

청구 일정은 계약 체결 뒤 실제 청구서를 발행하기 전에 회사가 청구 시점 금액 조건을 계획하는 단계다. 청구 일정 자체는 고객에게 발행한 청구서나 세금계산서가 아니다. 검수 완료와 같은 조건이 충족되면 청구 일정에서 청구를 만들고 청구를 근거로 세금계산서 발행자료를 확정한다.

## 테스트 역할

| 역할 | 책임 | 테스트에서 수행할 일 |
|---|---|---|
| 시스템 관리자 | 회사 환경과 권한 관리 | 조직 역할 직원 설정 자동화 감사 확인 |
| 인사 관리자 | 직원과 근무 기준 관리 | 가입 승인 근무정책 휴가 부여 자산 지급 |
| 일반 직원 | 회사 업무 수행 | 출퇴근 휴가 업무일지 주간보고 비용 등록 |
| 팀장 | 팀 업무와 결재 관리 | 휴가 승인 주간보고 확인 |
| 영업 담당자 | 매출 기회 관리 | 고객 영업기회 견적 계약 등록 |
| 견적 계약 승인자 | 거래 조건 통제 | 견적과 계약 승인 반려 이력 확인 |
| 프로젝트 관리자 | 계약 이행 관리 | 프로젝트 인력 문서 검수 일정 손익 관리 |
| 재무 담당자 | 매출과 수금 관리 | 청구 일정 청구 세금계산서 입금 수금배분 |

한 사람이 여러 역할을 가질 수 있지만 권한 검증을 위해 최소한 관리자 일반 직원 영업 담당자 프로젝트 관리자 재무 담당자 계정을 나누는 것이 좋다.

## 테스트 데이터

운영 데이터와 구분되는 이름을 사용한다. 실제 사업자등록번호 실제 고객 이메일 실제 카드번호를 임의로 사용하지 않는다.

| 구분 | 테스트 값 | 작성 원칙 |
|---|---|---|
| 조직 | 통합테스트팀 | 기존 조직과 겹치지 않게 작성 |
| 직원 | 통합테스트직원A | 테스트 전용 이메일 사용 |
| 고객사 | 통합테스트고객사 | 운영 고객과 혼동되지 않게 작성 |
| 사업자번호 | 테스트 환경에서 허용하는 미사용 번호 | 운영 실사업자번호 사용 금지 |
| 영업기회 | ERP 통합테스트 구축 | 예상 공급가액 100000000원 |
| 견적 | 공급가액 100000000원 | VAT 10000000원 총액 110000000원 |
| 계약 | 착수 30퍼센트 중도 40퍼센트 잔금 30퍼센트 | 승인 견적에서 전환 |
| 프로젝트 | ERP 통합테스트 프로젝트 | 계약에서 생성 |
| 청구 | 착수 30000000원 중도 40000000원 잔금 30000000원 | 각 금액에 VAT 별도 계산 |
| 입금 | 청구 총액과 일치하도록 분할 등록 | 부분입금과 완납을 모두 확인 |

기준일을 D0로 정한다. 프로젝트 시작일은 D0 종료일은 D0 이후 90일로 입력한다. 실제 테스트 날짜가 달라져도 같은 상대 순서를 유지한다.

## 테스트 시작 전 확인

1. Docker Desktop과 로컬 Supabase를 실행한다.
2. 개발 서버를 실행하고 `http://localhost:3000/api/health`가 200과 healthy를 반환하는지 확인한다.
3. 관리자 계정으로 로그인하고 감사 로그의 마지막 시각을 기록한다.
4. Excel의 테스트 실행 시트에 실행일 환경 빌드 식별자 테스트 담당자를 입력한다.
5. 기존 테스트 데이터가 있으면 이름 뒤에 실행일을 붙여 중복을 피한다.
6. LAN PC에서 테스트할 경우 APP URL 허용 Origin Supabase Redirect URL을 먼저 맞춘다.

## 단계 1 회사 운영 기반 준비

회사는 직원이 가입하기 전에 조직 권한 근무 기준을 준비한다. 이 단계의 완료 기준은 신규 직원을 승인했을 때 소속과 역할과 결재 경로를 지정할 수 있는 상태다.

| ID | 담당 | 수행 방법 | 성공 기준 |
|---|---|---|---|
| PRE 001 | 관리자 | 상태 점검 API와 로그인 화면을 연다 | health 200 로그인 화면 정상 콘솔 치명 오류 없음 |
| ORG 001 | 관리자 | 조직관리에서 통합테스트팀을 생성하고 상위 조직을 지정한다 | 조직도에 한 번만 표시되고 상세 조회 가능 |
| ORG 002 | 관리자 | 통합테스트팀 리더를 지정한다 | 리더가 조직 상세와 결재 경로에 반영 |
| RBAC 001 | 관리자 | 역할관리에서 직원 팀장 영업 프로젝트 재무 역할 권한을 확인한다 | 역할별 메뉴와 명령 권한이 업무 범위와 일치 |
| SYS 001 | 관리자 | 시스템 설정에서 회사 정보 공급자 세무정보 수금계좌 시간대를 확인한다 | 세금계산서와 청구에 필요한 필수값이 저장 |

실패가 발생하면 조직 ID 역할명 저장 요청의 HTTP 상태 Request ID를 기록한다. 마지막 관리자 역할을 제거하는 동작은 차단되어야 한다.

## 단계 2 직원 가입 승인 권한 확인

직원 등록은 Auth 계정 생성과 ERP 직원 상태 활성화를 모두 포함한다. 가입만 완료된 계정은 승인 대기 상태이며 회사 데이터에 접근하면 안 된다.

| ID | 담당 | 수행 방법 | 성공 기준 |
|---|---|---|---|
| USR 001 | 일반 직원 | 회원가입에서 테스트 이메일 이름 비밀번호를 입력하고 가입한다 | 가입 완료 안내와 확인 메일 생성 |
| USR 002 | 일반 직원 | Mailpit에서 확인 링크를 열고 승인 전 로그인한다 | 계정 상태 안내 화면으로 이동하고 업무 메뉴 접근 차단 |
| USR 003 | 관리자 | 가입 승인에서 사번 입사일 통합테스트팀 직급 직책을 입력해 승인한다 | 직원 상태 ACTIVE 직원 상세 조회 가능 |
| USR 004 | 관리자 | 직원 상세에서 일반 직원 역할을 적용한다 | 저장 성공 역할 이력 기록 |
| USR 005 | 일반 직원 | 로그아웃 후 다시 로그인한다 | 직원용 메뉴만 표시되고 대시보드 진입 |
| USR 006 | 일반 직원 | 관리자 URL을 직접 연다 | 403 또는 권한 없음 화면 표시 |
| USR 007 | 관리자 | 테스트 직원 비밀번호를 1로 초기화하고 임시 로그인 후 새 비밀번호로 변경한다 | 임시 비밀번호 로그인 가능 변경 후 이전 비밀번호 차단 |

로그인 실패 시 브라우저 개발자 도구의 요청 URL과 POST `/api/auth` 상태를 기록한다. 이메일과 비밀번호가 URL Query String에 노출되면 보안 이슈로 등록한다.

## 단계 3 근무정책 자산 장치 출퇴근

회사는 직원이 업무를 기록하기 전에 근무시간과 신뢰할 수 있는 장치 네트워크를 지정한다.

| ID | 담당 | 수행 방법 | 성공 기준 |
|---|---|---|---|
| ATT 001 | 인사 관리자 | 근무정책에서 근무시간 휴게시간 허용 요일 적용일을 등록한다 | 새 정책 버전 저장 이전 정책 이력 유지 |
| ATT 002 | 인사 관리자 | 테스트 직원에게 근무정책 적용 기간을 배정한다 | 직원 상세와 근태 화면에 정책 표시 |
| AST 001 | 자산 관리자 | 테스트 노트북 자산을 등록하고 직원에게 지급한다 | 열린 지급 이력 한 건 생성 |
| DEV 001 | 장치 관리자 | 지급 자산을 회사 장치로 등록하고 토큰을 1회 수령한다 | 장치 ACTIVE 토큰 재조회 불가 |
| ATT 003 | 관리자 | 출퇴근 검증에 회사 CIDR과 장치 요구 정책을 확인한다 | 현재 환경의 등록 기기와 회사 네트워크 판정이 표시 |
| ATT 004 | 일반 직원 | 내 근태에서 출근을 한 번 기록한다 | 서버 시각으로 출근 저장 중복 출근 차단 |
| ATT 005 | 일반 직원 | 같은 근무일에 퇴근을 기록한다 | 퇴근 저장 근무시간 계산 중복 퇴근 차단 |

외부 PC나 LAN 주소에서 출퇴근이 실패하면 화면의 등록 기기 확인 회사 네트워크 확인 실제 서버 ingress IP를 각각 기록한다. 단순히 브라우저에 표시된 공인 IP를 회사 CIDR로 등록했다고 통과하는 것으로 판단하지 않는다.

## 단계 4 휴가 결재 업무일지 주간보고

이 단계는 직원의 일상 업무가 결재와 프로젝트 원장으로 연결되는지 확인한다.

| ID | 담당 | 수행 방법 | 성공 기준 |
|---|---|---|---|
| LEV 001 | 인사 관리자 | 휴가관리에서 연차 15일을 부여한다 | 휴가 원장 GRANT와 잔액 15일 표시 |
| LEV 002 | 인사 관리자 | 1일 차감을 음수 조정으로 등록한다 | ADJUST 원장 생성 잔액 14일 |
| LEV 003 | 일반 직원 | 1일 휴가를 작성하고 제출한다 | 결재 진행 잔액 예약 결재자 알림 생성 |
| LEV 004 | 팀장 | 결재함에서 휴가를 승인한다 | 최종 승인 잔액 사용 근태에 휴가 반영 |
| WLG 001 | 일반 직원 | 업무일지에 일반 업무 2시간을 등록한다 | 해당 날짜 업무일지 저장 총시간 표시 |
| WLG 002 | 일반 직원 | 프로젝트 생성 전이므로 프로젝트 없는 내부 업무를 한 건 더 등록한다 | 업무 두 건과 합계가 정상 표시 |
| WRP 001 | 일반 직원 | 이번 주 주간보고를 생성하고 요약 차주 계획을 입력해 확정한다 | 확정 스냅샷 생성 Excel 다운로드 가능 |

잔액보다 큰 휴가와 겹치는 휴가가 차단되는지 별도 음수 테스트를 수행한다. 실패한 요청 때문에 잔액이 이중 차감되지 않았는지 확인한다.

## 단계 5 고객 영업기회 견적 계약

회사는 고객 정보를 기준으로 예상 매출을 만들고 내부 승인된 거래 조건을 계약으로 확정한다.

| ID | 담당 | 수행 방법 | 성공 기준 |
|---|---|---|---|
| CUS 001 | 영업 담당자 | 고객사에 상호 사업자정보 주소 업태 종목 세금계산서 이메일을 등록한다 | 고객 상세 조회 중복 사업자번호 차단 |
| SAL 001 | 영업 담당자 | 고객사에서 ERP 통합테스트 구축 영업기회를 등록한다 | 단계 LEAD 예상금액 100000000원 저장 |
| SAL 002 | 영업 담당자 | 단계를 QUALIFIED PROPOSAL 순서로 변경한다 | 변경 이력과 기대매출 계산 정상 |
| QUO 001 | 영업 담당자 | 영업기회에서 견적을 생성하고 유효기간 VAT 예상원가를 입력한다 | 견적번호 Revision 1 작성중 상태 |
| QUO 002 | 영업 담당자 | 인력 또는 용역 항목을 추가해 공급가액 합계 100000000원을 맞춘다 | 공급가액 VAT 총액 자동 계산 일치 |
| QUO 003 | 영업 담당자 | 내부 승인을 요청한다 | 현재 Revision 잠금 승인 대기 결재 생성 |
| QUO 004 | 승인자 | 금액과 항목을 확인해 승인한다 | 견적 상태 승인 승인자 시각 기록 |
| QUO 005 | 영업 담당자 | 견적서 PDF를 내려받는다 | 고객 공급자 항목 금액 Revision 승인 상태 표시 |
| CON 001 | 영업 담당자 | 승인 견적에서 계약 초안을 생성한다 | 원 견적 Revision과 계약 금액 연결 |
| CON 002 | 영업 담당자 | 계약 기간 청구조건 착수 30 중도 40 잔금 30을 입력한다 | 공급가액과 청구조건 합계 100퍼센트 |
| CON 003 | 승인자 | 계약을 승인하고 서명일과 서명 상태를 기록한다 | 계약 상태 서명 완료 프로젝트 생성 가능 |

## 단계 8 청구 일정 청구 세금계산서

청구 일정은 계약상 계획이고 청구는 고객에게 대금을 요청한 원장이다. 세금계산서는 청구를 세무 발행자료로 확정한 기록이다. 세 단계의 상태와 금액을 따로 확인한다.

| BIL 002 | 재무 담당자 | 중도 40000000원 잔금 30000000원 일정을 등록한다 | 일정 공급가액 합계 계약 공급가액과 일치 |

| BIL 004 | 재무 담당자 | 중도 청구도 같은 절차로 발행자료를 만든다 | 차수별 청구와 세금계산서가 각각 연결 |
| BIL 005 | 재무 담당자 | 최종검수 완료 후 잔금 일정에서 최종 청구를 발행한다 | 잔금 청구 33000000원과 입금기한 생성 |

## 세금계산서 실제 발행 수용 기준

세금계산서 기능은 PDF가 보이는 것만으로 통과하지 않는다. 다음 항목을 모두 확인한다.

1. 공급자 등록번호 상호 대표자 주소 업태 종목이 회사 설정과 일치한다.
2. 공급받는자 정보가 고객사 원장과 일치한다.
3. 공급가액 VAT 총액이 연결 청구와 원 단위로 일치한다.
4. 작성일 공급일 품목 수량 단가 이메일이 발행 채널 입력값과 일치한다.
5. 승인받은 발행 채널에서 실제 발급 성공을 확인한다.
6. 국세청 승인번호 발급시각 발급 채널을 ERP에 기록한다.
7. 같은 승인번호와 같은 청구의 중복 발행을 차단한다.
8. 취소 또는 수정세금계산서가 필요한 경우 원본을 삭제하지 않고 수정 이력을 남긴다.

## 실패 처리 규칙

실패한 단계마다 Excel 이슈 목록에 한 행을 만든다. 한 행에는 한 원인만 기록한다.

필수 정보는 시나리오 ID 환경 계정 역할 화면 주소 사전조건 재현 절차 기대 결과 실제 결과 HTTP 상태 오류 메시지 Request ID 관련 데이터 ID 증빙 파일이다. 비밀번호 세션 쿠키 API 키 서비스 역할 키 카드 전체 번호 주민번호는 기록하지 않는다.

### 진행 판단

- 통과 다음 단계로 진행한다.
- 실패 후속 단계가 해당 데이터에 의존하면 진행을 멈춘다.
- 차단 환경이나 계정 문제로 실행할 수 없으면 원인을 기록하고 환경을 복구한다.
- 보류 외부 홈택스나 승인 담당자가 필요한 경우 예정일과 담당자를 적는다.
- 재검증 수정 배포 후 같은 입력과 같은 역할로 다시 실행하고 결과를 덮어쓰지 않고 이력을 남긴다.

## 최종 통과 기준

1. 모든 필수 단계가 통과 또는 승인된 보류로 정리되어 있다.
2. 직원 승인부터 프로젝트 생성까지 데이터 연결이 끊기지 않는다.
3. 견적 계약 프로젝트 청구 세금계산서의 공급가액이 일치한다.
4. 입금 배분 후 프로젝트 미수잔액이 0원이다.
5. 승인 공수와 비용이 손익에 반영되고 마감 snapshot이 생성된다.
6. 일반 직원이 관리자 재무 감사 데이터를 볼 수 없다.
7. 이슈마다 수정 내용과 재검증 결과가 기록되어 있다.
8. 통합 보고서 감사 로그 자동화 실행 이력이 최종 증빙으로 보관되어 있다.
